# ตั้งค่าเวอร์ชัน Supabase และ Netlify

สถานะ: โค้ดนี้เป็นงานระหว่างพัฒนา ยังไม่ได้ทดสอบกับ Supabase จริง ยังไม่มีการ deploy และไม่ควรใช้รับออเดอร์จริงก่อนตรวจสิทธิ์และทดสอบครบ

1. SQL ใน `supabase/schema.sql` สร้างตารางแยกข้อมูลลูกค้าและออเดอร์ไว้ใน schema ส่วนตัว เปิด RLS สำหรับเมนู และ RPC สำหรับสั่งอาหารและหน้าพนักงาน จะสำเร็จได้เมื่อไม่มีตาราง/ฟังก์ชันชื่อเดียวกันอยู่ก่อน ตรวจโค้ดและสำรองฐานข้อมูลก่อนใช้งาน SQL นี้ไม่ใช่ขั้นตอนอัปเกรดฐานข้อมูลเดิม
2. สร้างผู้ใช้พนักงานจาก Supabase Dashboard → Authentication → Users โดยกำหนดอีเมลและรหัสผ่านแยกกัน จากนั้นผู้ดูแลกำหนดสิทธิ์ผ่าน SQL Editor ด้วย UUID จริงจากหน้า Users ตัวอย่าง (แทน UUID ก่อนรัน):

```sql
insert into restaurant_private.staff (user_id, role)
values ('UUID-ของแม่ครัว', 'kitchen'), ('UUID-ของแคชเชียร์', 'cashier');
```

บัญชีลูกค้าไม่ต้องลงชื่อเข้าใช้ ลูกค้าสามารถส่งออเดอร์ผ่าน RPC เท่านั้น แม่ครัวดูคิวและเปลี่ยนสถานะ แคชเชียร์ดูข้อมูลลูกค้า บันทึกชำระเงิน และเพิ่ม/เปิด/ปิดเมนู บัญชีที่ไม่มีสิทธิ์ไม่สามารถทำงานพนักงานได้
3. ใน Netlify ตั้ง build environment variables `SUPABASE_URL` และ `SUPABASE_PUBLISHABLE_KEY` ด้วย Project URL และ publishable key ของโปรเจกต์ที่ใช้งานจริง (หรือ legacy anon key หากจำเป็น) **ห้ามใส่ service_role หรือ secret key** ในตัวแปรนี้ เพราะค่าจะถูกใส่ลงใน JavaScript ที่ผู้ใช้ทุกคนอ่านได้
4. ติดตั้ง dependencies ด้วย `npm install` แล้ว Netlify build ใช้ `node scripts/prepare-cloud.js` และ publish `cloud/` ส่วน QR ใช้ Netlify Function และแพ็กเกจ qrcode หน้า Preview อาจสร้าง QR ที่ชี้ไปยัง URL production ของ Netlify ให้ทดสอบด้วย URL จริงก่อนพิมพ์
5. ทดสอบว่าลูกค้ามองไม่เห็นออเดอร์, แม่ครัวอ่านชื่อไม่ได้และบันทึกชำระเงินไม่ได้, แคชเชียร์เปลี่ยนสถานะครัวไม่ได้, ราคาถูกกำหนดจากฐานข้อมูล, QR เปิดโต๊ะถูกต้อง และข้อมูลอยู่หลังรีเฟรช ทดสอบ login, การหมดอายุ session, backup และกู้คืน ก่อนนำไปใช้

ความเสี่ยงที่ยังต้องพัฒนา: คำสั่งสั่งอาหารสาธารณะยังไม่มี rate limiting หรือระบบกันสแปม, ยังไม่รวมการสำรองรูป Storage, ยังไม่รองรับ refresh token (เมื่อ session หมดอายุพนักงานต้องเข้าสู่ระบบใหม่) และยังไม่มีการยืนยันการชำระเงินจริง อย่านำโค้ดนี้ไปใช้รับข้อมูลลูกค้าหรือออเดอร์จริงจนกว่าจะปิดช่องโหว่และทดสอบ end-to-end
